Publishing a vault

What the build does to a folder of notes, and which parts of it you are expected to look at before anyone else does.

A publish walks the vault once, renders every note through Obsidian's own renderer, and writes the result to a folder of plain HTML. Nothing in the output needs a server: the pages open from disk, the links between them resolve as files, and the whole thing can be dropped onto static hosting without a build step at the other end.

What the preview adds

A preview build is the same output with a review overlay inlined into every page. The overlay is the only difference, and it is deliberately the last thing written: the article markup is never touched, so what you read in a preview is what a publish would have produced, down to the whitespace.

A preview that edits the page to review the page is not a preview of anything. Everything the overlay draws lives in a shadow root, and nothing in it reaches back out.

Marks travel with the words

A comment is recorded against a block, not a pixel. The drop point is stored as a fraction across and down the block it landed on, so a pin comes back to the same few words after a rebuild, a reflow, or at a window width nobody tested. A pin dropped where no block covers the point keeps plain document coordinates instead, and says so.

$ npm run build
$ npm run deploy
  vault is open in Obsidian
  hot-reload is enabled: the plugin will reload on its own

Two separate things have to be true before a change is testable, which is why the deploy reports on both. A copy into a watched folder and a copy into an unwatched one look identical from the outside, and only one of them is a change you can see.

What gets left out

  • Folders listed as excluded, and everything under them.
  • Notes whose frontmatter asks to stay private.
  • Attachments nothing in the published set links to.
  • The review overlay itself, on a real publish.

Exclusion is checked twice — once when the set of pages is chosen, and again when links are rewritten — because a link into a folder that was never published is the one failure a reader meets as a dead end rather than as a missing page.

Where the output lands

PartWritten toRebuilt
Pages/when the note changes
Harvested CSS/assets/site.csswhen the theme changes
Client script/assets/site.json every build
Attachments/assets/when linked

The incremental path compares a hash of each note's rendered output against the last build's, so a publish after a one-word edit rewrites one page and leaves the rest alone. The hash covers the rendered HTML rather than the source, which means a theme change correctly invalidates everything and a frontmatter-only edit correctly invalidates nothing.

Anything the build could not resolve is collected and reported at the end rather than thrown at the point it was found. A publish that stops halfway leaves a half-written site, and a half-written site is worse than a complete one with a list of things to fix.
